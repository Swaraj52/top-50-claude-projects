# Architecture: Daily Review Agent (Project 03), "Shutdown"

## Overview

```text
Browser ──HTML forms / HTMX──▶ FastAPI (Jinja2 templates)
                                 ├── routes: auth, today, tasks, log, blockers, checkin,
                                 │           review, trends, history, settings
                                 ├── services: day (snapshot), planner (tomorrow plan),
                                 │             reviewer (Claude or rules), trends (stats + SVG)
                                 └── SQLAlchemy ──▶ SQLite (data/shutdown.db), Alembic migrations
                                                └──▶ Claude API (optional, review narrative)
```

One process on port **8003** serves pages, HTMX fragments and static files (`app/static`, including a
vendored `htmx.min.js`). There's no Node toolchain. Every page works without JavaScript: forms post and
redirect. HTMX upgrades the common actions (toggle task, add log entry, resolve blocker) to in-place
fragment swaps.

## Data model

```text
users(id, email UNIQUE, name, password_hash, timezone, capacity_hours, created_at)
sessions(id, user_id, token_hash UNIQUE, csrf_token, created_at, expires_at)
tasks(id, user_id, title, area, priority[1..3], estimate_min, status[todo|doing|done|dropped],
      planned_for DATE?, due_date DATE?, carry_count, completed_at?, created_at)
log_entries(id, user_id, day DATE, kind[done|win|learning|note], text, minutes?, task_id?, created_at)
blockers(id, user_id, text, task_id?, opened_on DATE, resolved_on DATE?, created_at)
checkins(id, user_id, day DATE, energy 1..5, mood 1..5, focus_hours, UNIQUE(user_id, day))
reviews(id, user_id, day DATE, source[ai|rule], model?, note?, content JSON,
        plan JSON, committed, created_at, UNIQUE(user_id, day))
```

"Today" is computed in the user's IANA timezone. `planned_for` is the day a task is planned to be
worked on. A task appears on Today when `planned_for <= today` and it isn't done or dropped. Carrying a
task over increments `carry_count`, which the planner and the trends use.

## Review pipeline

1. **Snapshot** (`services/day.py`): done tasks, in-progress and unfinished tasks, log entries,
   open blockers (with age), the check-in, capacity.
2. **Planner** (`services/planner.py`, deterministic): candidates are unfinished tasks plus tasks
   planned or due tomorrow. They're scored by priority, overdue/due date, carry count (rising urgency)
   and age, then greedily filled up to the capacity (default 6 h, 30 min default estimate). This
   always runs, so the plan stays valid even if the AI fails.
3. **Reviewer** (`services/reviewer.py`):
   - With `ANTHROPIC_API_KEY`: one Messages API call to `claude-opus-5-5` (structured JSON output,
     effort `low`, server-side refusal fallback) that writes `{headline, recap, wins[], blockers[],
     tomorrow_focus[{task_id, why}], reflection_question}`. It receives the snapshot and the planner's
     candidate list. It may re-order the plan but **only with candidate task ids**, and the result is
     re-checked against capacity. Invalid JSON, refusal, truncation or API errors fall back to the rules,
     with a visible note.
   - Without a key: a rule-based review (recap from counts and entries, blocker ages, recurring blocker
     warning, the planner's top items with reasons, a rotating reflection question).
4. **Commit** sets `planned_for = tomorrow` (in plan order) for kept tasks, and marks dropped ones
   `dropped`. Unfinished tasks the user chose to carry over get `carry_count + 1`.

## Trends (`services/trends.py`)

All computed per local day for the last 7 or 14 days: completed tasks, carry-overs, focus hours,
energy and mood, blockers opened and resolved, review streak, minutes by area. Charts are inline
SVG generated by small server-side functions (bar and line), with `<title>` and a visually hidden
data table for screen readers.

## Security

- scrypt passwords; HttpOnly SameSite=Lax session cookie (only its SHA-256 is stored).
- **CSRF:** a per-session synchronizer token, sent as a hidden `csrf_token` field in every form and
  as an `X-CSRF-Token` header on HTMX requests (set once via `hx-headers` on `<body>`), and checked
  with a constant-time compare on every unsafe request.
- Login rate limiting, per-user scoping (404 for other users' rows), Jinja2 autoescaping for all
  user content, and a Content-Security-Policy that allows only self-hosted scripts.

## Testing

pytest + TestClient: auth and CSRF rejection, every route's happy path and validation, HTMX
fragments, isolation, day boundaries in a non-UTC timezone, the planner (capacity, scoring,
carry-over), the reviewer (rules, AI fake, invalid task ids, failure fallbacks), trends maths and
SVG output, migrations matching the models.
